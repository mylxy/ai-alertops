# AI 执行与修复交付流程

版本：V1；日期：2026-10-05。执行器使用固定服务器 Docker 中的 Codex CLI。本文定义[整体方案](README.md)中的任务调度、执行进度、Git 分支与 Codeup MR 交付；数据库字段见[数据库设计](database.md)。尚未部署执行器或验证真实自动修复。

## 1. 执行边界

新 LOG 轮次在创建告警时同时创建唯一 AI 任务。METRIC、NOTICE 不创建任务；同轮重复事件、人工备注、MR 回调都不再次运行 AI。每轮至多执行一次，失败交给人工，首版不提供自动重跑或手动重试。

**每个项目最多 3 个修复任务处于执行阶段，其余 FIFO 排队。** 不同项目可在服务器总容量内并行；排队任务不会因为超过三个而丢失。

每个项目预置三个固定修复工作区，各自独立克隆项目仓库，容器直接修改分配到的工作区。一个工作区同时只服务一个任务，排查、切分支、修改、验证及提交全程独占；使用普通 Git 分支，不使用 worktree，也不在每次任务开始时重新克隆。

领取顺序由 `(queued_time, id)` 确定。调度器在短事务内锁项目和候选工作区，选择最早的可执行任务及一个 READY 工作区，保存任务归属、占用状态与分配版本，提交后才创建容器。已关闭的排队轮次直接 SKIPPED，不占目录。STARTING、RUNNING、FINALIZING 均占名额；没有可用工作区时保留排队状态。

每次领取增加工作区的分配版本；任务回收须同时匹配原任务与版本。工作区为 OCCUPIED 或 BLOCKED 时不能再分配，心跳超时也不直接释放。单个工作区阻塞时，其他健康工作区继续服务队列；全部占用或阻塞时等待，不能临时新增第四个工作区。

AI 容器只能操作分配给任务的项目目录；宿主机执行进程管理容器，Codex 容器不挂载 Docker socket。告警中的 Message、代码仓库内容和远程结果作为排查输入，不能据此扩大宿主机或其他项目访问范围。

## 2. 容器、目录与 Skill

每次任务创建新容器，结束后清理容器；固定工作目录与提交的修复分支按交付策略保留。读写挂载路径位于 Docker daemon 所在固定服务器，不能把登录用户电脑上的路径当作服务器目录。

宿主机目录布局示例（实际根路径在部署时配置）：

```text
/srv/alertops/projects/zhixiangyun/
  slot-1/          # 独立仓库克隆、Skill 和项目文档
  slot-2/          # 同样的仓库映射，独立 .git 与工作文件
  slot-3/          # 同样的仓库映射，独立 .git 与工作文件
```

各工作区按统一的仓库相对路径组织多仓库代码。容器只把自己分配到的 slot 读写挂载为 `/workspace`，不挂载包含其他 slot 的项目父目录。仓库索引、Git 元数据、构建输出和可写 CLI 状态均隔离；路径校验包含符号链接解析，不能把不同路径名误当成不同目录。

Skill 与项目文档在三个工作区按受控基线准备，按 CLI 支持的目录布局发现和加载；基线更新在项目无活动任务时执行，既有异常现场不能被覆盖。任务开始时记录本工作区的配置版本，任务产物另存到按任务 ID 隔离的持久目录，供后续回调和查询使用，不因工作区复用而覆盖。

容器镜像包含固定版本的 Codex CLI、Git 和项目需要的构建运行时；宿主机目录有源代码、Skill 和文档，不意味着容器里已经有宿主机安装的命令或依赖。挂载后按已验证的 Skill 目录布局和发现规则加载，并在任务记录中保留镜像、Skill/配置版本及仓库基线。

任务输入包含：告警编号、轮次与任务 ID、异常证据、可信资源映射、部署版本（能取得时）、受影响仓库候选、允许目录、分支规范、目标 master、验证要求及进度回报协议。新日志和人工备注后续继续进入告警历史，不把它们当成对正在执行的 Codex 会话追加指令。

项目内已有 AGENTS/Skill 可以继续使用；本平台任务必须明确授权普通 hotfix 分支和挂载目录内开发方式，防止继承到与本次已确认流程冲突的 worktree 或 codex 分支前缀。若目录内规则确实无法满足任务要求，报告冲突并失败，不自动修改团队共享规则文件。

Git、Codeup 和 Codex 凭据由执行进程通过受控运行配置注入；不写入提示词、仓库、卡片、日志正文或业务表。不同容器使用各自的可写 CLI 会话/缓存目录，避免共用可写认证状态。网络、文件权限、资源和任务总时长按所需范围配置，不能依靠无人值守就默认关闭所有限制。

## 3. Codex CLI 调用与事件协议

使用非交互模式 `codex exec`。调用参数由执行进程固定生成，主要使用工作目录选项、JSONL 事件输出、最终输出 schema 和结果文件；告警正文作为数据输入，不拼接为宿主机 shell 命令。

| 通道 | 内容 | 平台处理 |
| --- | --- | --- |
| CLI JSONL | thread/turn/item 生命周期、错误、命令等执行证据 | 记录实际启动、运行与失败，保留必要诊断信息 |
| 业务进度报告 | 定位结果、受影响仓库、验证结果、MR 交付等结构化事件 | 校验后落库、追加处理记录、更新卡片 |
| 最终结构化输出 | 本次业务结论、必要仓库集合、分支/提交、MR 清单、验证摘要、未完成项 | 核对过程记录并封口交付集合 |

Codex 原生 JSONL 不等于平台业务协议：不能搜索自然语言里的“定位成功”就改变状态。镜像内提供一个任务进度上报入口，Skill 明确在关键节点调用；宿主机执行进程验证并转交平台，最终结构化输出作完整性核对。

最小业务事件类型：`EXECUTION_STARTED`、`ROOT_CAUSE_LOCATED`、`REPAIR_PROGRESS`、`VERIFICATION_FINISHED`、`MR_CREATED`、`EXECUTION_FINISHED`、`EXECUTION_FAILED`。事件包含任务 ID、执行令牌、顺序号、发生时间及对应结构化 payload。令牌与任务绑定，顺序号用于幂等和拒绝倒退；服务端验证引用的仓库、MR 和轮次，不信任 AI 自报的任意数据库 ID。

Docker 返回容器 ID 只说明容器已创建，不能据此把日志卡改为处理中。执行进程确认 Codex 已进入实际执行并完成启动门槛后，才报告 `EXECUTION_STARTED`。定位事件必须包含证据、问题位置与结论；创建 MR 的事件必须有可核实的仓库、分支、提交和 MR 身份。

关键进度持久化确认后再前进；暂时上报失败在任务自己的产物目录保存待发送记录并重传。重传仅重报事件，不重新运行修改或再次创建 MR。最终结果缺失、schema 不合法、进度与最终清单冲突时，任务不能标为完整成功。

命令使用的沙箱和批准设置须满足容器内写代码及必要网络访问，按固定镜像版本验证。本文不提供默认绕过限制的启动命令。项目根目录如果不是 Git 仓库，应明确传入工作目录并验证 CLI 的相关选项，不假定挂载多仓库目录自动满足 CLI 检查。

依据：[Codex 非交互模式官方文档](https://learn.chatgpt.com/docs/non-interactive-mode)及本机 `codex exec --help`；真实部署前以锁定的镜像版本复核参数、事件格式和 Skill 加载结果。

## 4. 从排查到修复分支

1. 领取任务前检查项目配置、路径、仓库映射及工作目录可用性。发现未知未提交修改、不完整 Git 操作或失效凭据时停止，不用强制清理来掩盖问题。
2. 容器在分配的项目目录下读取异常日志、部署证据、项目代码与 Skill，完成定位。定位到问题后上报证据并更新卡片；无法定位或判断无问题时也给出结构化结论。
3. 确认需要修改的仓库，先保存 `alert_ai_task_repo` 记录，再执行修改。不能只在创建 MR 成功后才记录仓库，否则部分失败会从交付范围中消失。
4. 获取各仓库最新 `origin/master`，保存精确基线提交；如部署版本不同，排查时保留该事实，修复分支仍按确认要求基于 master。若问题只存在旧版本或无法合理适用于 master，说明原因，不擅自换目标分支。
5. 在第一个 Git 分支创建前一次性分配并保存 `hotfix-YYYYMMDD-HHmmssSSS-<alert_no>`，例如 `hotfix-20261005-143000123-AL000123`。后续仓库复用同一任务分支名；重试使用已保存名字，不重新取当前时间。
6. 在相关仓库使用普通 Git 分支修改、运行有意义的验证，保留命令、结果与限制。分支冲突先核实是不是本任务已创建的分支，不能覆盖来源不明分支或强推他人内容。
7. 提交并推送到对应修复分支，向 master 创建 MR，标题与说明包含告警编号、问题、修复、验证及剩余风险。一个任务可有 0、1 或多个 MR，按实际修复范围保存动态列表。
8. 核对必要仓库全部有明确交付结果，封口清单；保存最终结果和产物。容器完成本次任务后退出，不等评审和合并才释放执行名额。

以上为平台运行时的分支规则：不使用 codex 前缀，不使用 Git worktree。编写本设计文档时使用的仓库任务 worktree 属于文档仓库开发规范，与线上 AI 修复方式无关。

## 5. 多个 MR 与合并回调

Codeup MR 关系为“告警轮次 → AI 任务 → 受影响仓库 → 多个 MR”。卡片按记录动态生成名称、链接和各自状态，不设计固定的一号、二号 MR 槽位。超过钉钉单卡内容承载能力时展示准确汇总和“查看全部 N 个合并请求”的已登录 H5 入口，完整列表不丢失、不把未展示项视为不存在。

| 事实 | 卡片含义 |
| --- | --- |
| Codex 正常结束，但无法定位 | 展示无法定位及依据，等待人工处理 |
| 已定位并提交部分 MR，另一个必要仓库失败 | 展示部分交付及失败项，不能显示修复交付完成 |
| 必要 MR 都已创建 | 展示完整待评审/待合并列表，不表示已上线 |
| 某 MR 评审通过，仍未合并 | 该项显示评审通过/待合并 |
| 某 MR 已实际合并到 master | 该项显示已合并及合并提交 |
| 完整必要集合均已实际合并 | 显示修复分支全部已合并；日志主状态仍按人工处理规则 |

人通过卡片链接到 Codeup 评审和合并。Codeup Hook 到达后先验来源、持久化，再按组织/仓库/MR 身份匹配；不明、重复或乱序的通知读取 Codeup 当前状态核实。只有真实 `MERGED` 且目标 master、源分支和提交关系符合记录，才标记已合并；“点击通过”如果只是批准评审，不能直接更新为已合并。

更新 MR 当前状态、追加原轮次记录并安排卡片同步在一个事务完成。外部重复回调、旧分支回调和关闭轮次后的回调都不能影响同类问题的新轮次。回调先于 MR 关联记录时保存待协调事件，等待核实，不按项目最新任务猜归属。

创建分支、推送或创建 MR 返回超时未知时，先用固定任务、仓库、分支和提交信息查询已存在结果，再决定补做；不能因传输重试多开 MR。平台可对未终结 MR 做有间隔的状态核对以弥补漏回调，不重新执行 AI。

官方依据：[Codeup Webhooks 配置](https://help.aliyun.com/zh/yunxiao/user-guide/webhooks-settings)、[查询合并请求](https://help.aliyun.com/zh/yunxiao/developer-reference/getchangerequest-query-merge-request)。接入时区分 reviewOpinionStatus 与合并请求 status，并确认当前 API 的不可变 ID、显示编号和回调字段映射。

## 6. 人工结束、失败与恢复

| 情形 | 任务与工作目录 | 告警与卡片 |
| --- | --- | --- |
| 排队时人工结束 | 任务 SKIPPED，不启动容器 | 保持已处理 |
| 容器准备中但 Codex 未实际执行时结束 | 启动门槛重新校验，跳过并回收空闲资源 | 保持已处理，不误报 AI 接入 |
| Codex 已开始后人工结束 | 继续本次执行与必要收尾 | 后续结果仅追加原轮次，不覆盖人工结论 |
| Docker/CLI 启动失败 | FAILED，保存原因，不自动重跑 | 没有其他处理动作则仍待处理；已有备注则保持处理中 |
| 排查或修复中失败、超时 | 确认执行停止，保存日志、分支和现有 MR；未知修改保留待检查 | 展示失败及已交付部分，不自动关闭 |
| 卡片投递失败 | 只重试同步任务 | 业务和 AI 结果保留，不重新运行 AI |
| 服务器或执行进程重启 | 先核对 Docker 容器、进程与数据库任务，再恢复观察或收尾 | 恢复展示已保存进度，不创建第二个任务 |

容器使用稳定任务名和任务标签，重启后按固定服务器实际容器状态协调。心跳丢失或租约到期不能证明旧执行已停止；确认旧容器退出且不存在仍写该目录的任务进程前，不能把目录交给新任务。协调不明时阻塞相应执行资源并展示原因，不冒险启动替代容器。

正常收尾需要：保存最终输出和必要产物、确认容器停止、检查工作目录没有未归档修改或未完成的 Git 操作。执行进程完成这些检查后，在事务内核对工作区的当前任务和分配版本，将任务改为终态、清空占用并将工作区恢复 READY；旧执行进程的迟到回收请求不能释放新的占用。

保留修复分支，下一任务从最新 master 建自己的新分支；待评审 MR 不占执行名额。若工作区有未知脏文件或冲突，保留现场并标为 BLOCKED，另外两个健康工作区仍可执行。旧容器是否停止尚不明确时，继续保留活动任务关联；管理员在服务器处理并完成检查后才可恢复可用。禁止自动 `reset --hard`、`clean -fd` 或删除分支来清场。

一个任务跨多个仓库部分成功时，已推送分支和已创建 MR 继续可查；失败没有取消 MR、自动合并或发布的含义。发布由现有人工/CI 流程完成，告警平台只记录用户提供的处理结果。

并行任务的 MR 可能修改同一段代码；独立工作区解决本地文件互相覆盖，分支间冲突仍由 Codeup 评审及现有 CI 流程核实、人工处理。本版不因合并冲突自动再次启动已结束的 AI 任务。

## 7. 验收场景

- 同一轮次连续收到多个 Hook，仅生成一个 AI 任务；不同轮次保留不同告警编号和分支名。
- 同项目连续 5 个任务最多同时执行 3 个，另外 2 个按 FIFO 等待；不同项目共享服务器总容量但互不串目录。
- 并发任务切分支、写代码及构建产物互不影响；真实路径或符号链接重叠的错误配置被拒绝。
- 单个工作区阻塞时另外两个继续工作，三个都不可用时任务保持排队；不存在用第四个目录绕过上限的路径。
- 两个调度进程竞争同一工作区只允许一个成功；旧任务的迟到回收请求不能释放已经分配给新任务的目录。
- 领取、容器创建、CLI 实际开始三个时点可区分；人工关闭与启动竞争的结果确定且可审计。
- Docker 创建后进程重启、Codex 仍运行但心跳中断时，不出现双开或同目录双写。
- 单仓库、多仓库、三条以上 MR、创建 MR 前失败、评审通过未合并、部分合并、全部合并均准确展示。
- 任务已结束、轮次已关闭或下一轮已产生后，旧任务和旧 MR 回调只更新原轮次。
- 最终结果缺失、凭据失效、构建不可用、目录脏、通知失败和结果未知各有明确记录，不伪装为成功。

Docker 挂载行为依据[官方 bind mounts 文档](https://docs.docker.com/engine/storage/bind-mounts/)。本次只完成流程设计，未创建镜像、启动容器、修改业务仓库或提交真实 MR。
