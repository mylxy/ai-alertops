# 吊顶与告警处理工作台设计

2026-10-05 确认的主流程：吊顶统计当前群日志告警和指标告警；按钮打开 H5 列表；在 H5 查看、备注或完成处理；成功提交且产生卡片可见的业务变更后，向当前群发送一张最新卡片。无有效变更时不新增群消息。

本文是设计与验收依据。[本地交互原型](alert-workbench.prototype.html)展示吊顶、群卡片、H5 侧栏、完整页面和手机半浮层，并在内存中模拟业务状态与消息联动。吊顶 H5 入口新草稿已生成并保存，普通群测试卡已投放。当前未实现生产 H5 或真实业务联动，也未开启群内真实吊顶。

完整的已确认方案、后续设计边界及已验证范围见[告警卡片方案确认](告警卡片方案确认.md)；本文细化跨入口联动，不扩展其他产品设计。

## 吊顶统计与入口

吊顶只展示当前群的未完成告警，按日志、指标分别统计。推荐布局：

| 类型 | 待处理 | 处理中 | 未完成 |
| --- | ---: | ---: | ---: |
| 日志告警 | 3 | 1 | 4 |
| 指标告警 | 1 | 1 | 2 |

底部提供一个按钮：**查看未完成（6）**。这是用户提出的“待处理”快捷入口；使用“未完成”文案，明确包含待处理和处理中。点击默认显示全部未完成事项，在 H5 中切换日志或指标。

统计按告警事项/轮次去重：重复日志、累计发生次数、多条群卡片消息均不增加事项数。首条备注使待处理变为处理中，合计不变；日志已处理、指标已恢复才减去对应事项。待处理与处理中合计大于 0 时才展示吊顶；仅有处理中事项也展示。合计为 0 时默认不展示，已开启的吊顶应关闭并移除整块区域，不显示零数量卡片或空白占位。新的未完成事项出现后重新开启。已打开的 H5 保留当前结果或空列表，不因吊顶关闭而被强制退出。

## H5 展示与操作

H5 标题为“本群未完成告警”，显示来源群名称。默认展示当前群的待处理与处理中，分类为“全部 / 日志告警 / 指标告警”。完成项从默认列表移除；已打开的完成详情保留处理结果并变为只读，便于用户确认提交结果。

每项展示类型、当前状态、问题标题、服务或资源、首次/最近发生时间及最近备注。日志详情包含异常证据、次数、AI/MR 结果和处理记录；指标详情包含当前指标值、阈值、触发/恢复信息和处理记录。长列表分批加载，避免在一个页面堆叠全部长日志。

H5 卡片应尽量与对应的钉钉模板一致，包括字段顺序、状态标题、颜色、字号、信息块、备注和按钮。不得为了美化另加趋势图、柱形图、插图或模板中没有的指标。外层筛选与计数属于列表导航；不改变日志、指标各自的卡片结构。

| 类型 | 待处理、处理中允许的操作 | 终态 |
| --- | --- | --- |
| 日志告警 | 添加备注；标记已处理并填写一句处理结果 | 已处理；禁止追加备注 |
| 指标告警 | 添加备注；由监控的有效恢复事件结束 | 已恢复；禁止追加备注 |

人工备注仍为可选，不要求先认领或接管。首条备注成功后转为处理中；后续备注追加历史，保持处理中。只填写草稿、取消或保存失败不会改变状态。添加备注不启动、暂停或重试 AI。

## 哪些操作发送群消息

“卡片更新”指成功保存的业务内容变化，包括新增备注、处理结果及状态，不按渲染次数、更新时间字段或页面是否刷新判断。

| 操作或事件 | 更新业务记录和展示 | 新增群卡片消息 |
| --- | --- | --- |
| 打开 H5、查看详情、切换筛选、刷新、复制内容 | 只读取当前状态 | 否 |
| 输入但未提交、取消、空白校验失败、保存失败 | 不保存 | 否 |
| H5 成功追加一条备注 | 追加备注；必要时转为处理中 | 是，一张最新卡片 |
| H5 成功标记日志已处理 | 保存处理结果、人员、时间和终态 | 是，一张已处理卡片 |
| 同一次提交同时改变备注和主状态 | 合并为一次有效业务提交 | 是，仍只有一张 |
| 重复点击、超时后重试同一提交 | 返回同一次提交结果 | 不重复发送 |
| 对已处理/已恢复事项提交备注 | 拒绝提交，返回最新终态 | 否 |
| 已完成事项再次请求完成 | 返回已完成结果，不覆盖处理人或结论 | 否 |
| 自动事件、AI/MR 进度、指标恢复 | 沿用既定业务规则同步已有展示 | 本次不增加逐次重发规则 |
| 在原群卡片中操作 | 沿用现有回调更新规则 | 本次新增消息规则限定为 H5 有效提交 |

每次成功提交即时触发通知，不等用户关闭 H5 或离开页面；多个告警分别提交，分别通知。只发送发生变化的告警，不把整页重新发送。每轮告警仅归属一个固定群；来源群必须与归属群一致，通知只发到这个群。

“相同文字”不等于重复请求：用户主动再次追加同样文字，或另一人提交同样文字，仍是新的处理记录；只有同一次提交的重试应去重。卡片仍按现有设计显示最近三条备注并保留完整历史入口。

## 原卡、新消息和统计的一致性

同一告警轮次可以对应多条钉钉卡片消息：首次告警通知，以及 H5 有效提交后的更新通知。新发消息绑定原业务轮次，使用独立的消息投递标识；它不会创建新问题、增加未完成数量、重置累计次数或重新执行 AI。

已有原卡和后续通知卡统一展示本轮最新状态，后续变化同步所有已投放实例。任意旧卡按钮或旧 H5 页面都必须按服务端当前状态校验；不能因为旧卡仍显示按钮，就允许向终态追加备注。

处理顺序的逻辑契约为：

1. 校验当前用户、来源群、目标轮次、请求标识和允许的操作。
2. 成功保存业务变更，产生一次有效提交；没有变更则结束，不安排通知。
3. 根据最新业务数据刷新 H5、吊顶统计及已有卡片，向来源群投放一次最新卡片通知。
4. 对失败的群同步或投递重试，复用同一次提交对应的投递标识，不能再创建一条业务备注。

钉钉消息并非业务事实来源。卡片同步失败不撤销已保存备注；H5 区分“保存失败”和“已保存，群消息同步中/失败”，由后台重试同步。发送结果超时未知时先核实或依靠已验证的幂等投递机制，不盲目换新实例 ID 重发。具体重试参数在实现时确定。

并发时，较旧的操作不能覆盖较新的展示状态。备注与完成竞争，以服务端保存顺序为准：备注先成功则保留；完成先成功则拒绝后到备注。指标在提交备注期间恢复，也必须按已恢复状态拒绝后到写入。通知投递前读取最新状态，避免发送已过期的“待处理”视图。

## 一次操作示例

初始未完成共 6 项，其中日志待处理 3、处理中 1；指标待处理 1、处理中 1。

1. 用户从吊顶打开 H5，查看两项告警但未修改：没有新增群消息。
2. 给一项待处理日志添加“已定位，正在修复”：日志待处理变为 2、处理中变为 2，未完成总数仍为 6；原卡及已有通知卡更新，群内新增一张橙色最新卡。
3. 继续追加“已提交测试”：仍为处理中，总数仍为 6；因为新增了处理记录，再发送一张最新卡。
4. 修复验证完成，填写结果并标记已处理：该项从 H5 未完成列表移除，总数变为 5；已有卡片同步绿色，群内新增一张绿色已处理卡。
5. 用户重复点击提交或关闭页面：不再新增消息；已处理详情禁止备注。

## 钉钉接入边界

- 吊顶群聊接口要求场景群或安装群聊酷应用的群。普通群只有机器人不能视为已满足条件。[创建并开启互动卡片吊顶](https://open.dingtalk.com/document/development/send-group-helper-message)
- 模板条件隐藏不足以撤下整个群顶部区域；合计归零时使用公开[关闭互动卡片吊顶](https://open.dingtalk.com/document/development/close-interactive-card-ceiling)接口，`POST /v2.0/im/topBoxes/close`。显隐按最新群统计协调，避免旧关闭请求覆盖新告警。
- H5 入口必须指定钉钉容器：PC 使用 `dingtalk://dingtalkclient/page/link?pc_slide=true&url=<编码后的 H5 URL>`，手机使用 `im_open_hybrid_panel` 半浮层协议，通过 `open_platform_link` 的 `pcLink` / `mobileLink` 分流并分别编码。普通 HTTP 链接在 PC 默认走系统浏览器，不能直接用作本需求的卡片入口。[链接跳转规范](https://open.dingtalk.com/document/development/link-jump-specification)
- 在钉钉中加载独立工作台内容，不能再套原型的模拟群聊、浏览器边框或视图切换栏。原型通过 `?variant=workspace&embed=1` 提供此布局；关闭使用钉钉自身侧栏按钮。
- 卡片实例、业务轮次和群消息不是同一个标识；新增消息需要独立且可重试复用的投递标识，不能假设更新原实例会把旧消息自动移到群底部。[创建并投放卡片](https://open.dingtalk.com/document/orgapp/create-and-deliver-cards)
- H5 必须登录，使用已验证的企业钉钉身份；账号可用且当前仍属于来源群的用户可备注本群未完成告警、标记本群日志已处理，不限指定运维人员。来源群须等于轮次固定归属群，不能只凭 URL 中的群 ID 授权。首次登录默认为普通用户；后台查询全平台告警，管理员额外维护配置。完整权限见[平台整体设计](../platform/README.md)。消息投递使用企业应用公开服务端 API，不接入 CLI/MCP。

## 验收要点

- 日志、指标分别统计；待处理转处理中不减少合计；同轮多卡只计一次。
- 合计为零时不展示吊顶；仅有处理中事项仍展示；最后一项结束后关闭吊顶，新事项出现后重新开启。隐藏不删除历史消息、不关闭已打开的 H5。
- H5 默认包含两类未完成状态；完成后列表移除，详情只读；分类筛选不会发送消息。
- 首条与后续备注均产生一条最新卡片通知；一次提交多字段变化仍只有一条。
- 浏览、取消、无效输入、保存失败、重复提交及无变化不新增群消息。
- 群同步失败后业务记录保留；重试不重复备注或通知，较旧数据不覆盖新状态。
- 原卡和新发卡状态一致，所有旧入口拒绝对已处理/已恢复事项追加备注。
- 两人并发、指标恢复与备注并发、其他群链接或越权请求有明确结果，不串群或串轮次。
- Mac 与手机从吊顶打开正确来源群页面，真实 H5 提交、群消息发送及同步链路均通过验收。
