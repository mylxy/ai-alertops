# 告警卡片方案确认

确认日期：2026-10-05。本文汇总本轮已确认的卡片、处理流程、状态变化和吊顶规则，作为后续实现与验收的统一入口。本文不新增生产实现，也不表示所有客户端与后端链路已验证。

详细依据为[日志卡设计](日志告警卡片设计说明.md)、[指标卡设计](../../../design/metric-alert-card/指标告警卡片实现说明.md)、[吊顶模板](../../../design/alert-ceiling-card/README.md)和[吊顶与 H5 联动](吊顶与告警处理工作台设计.md)。旧版编号定位、一次性备注、恢复后补记、独立认领和上线观察流程不再作为本版依据。

## 已确认的卡片范围

| 卡片或入口 | 职责 | 是否进入未完成统计 |
| --- | --- | --- |
| 日志告警卡 | 展示异常、AI/MR 进展、人工备注和处理结果 | 待处理、处理中计入；已处理移出 |
| 指标告警卡 | 展示指标告警、人工备注和监控恢复结果 | 待处理、处理中计入；已恢复移出 |
| 吊顶统计卡 | 汇总本群日志和指标的未完成数量，提供 H5 入口 | 自身不是告警，不计数 |
| H5 告警处理工作台 | 展示本群未完成告警，沿用对应卡片内容和操作 | 与群卡片统计同一批事项，不另建事项 |
| NOTICE 业务提示卡 | 展示业务通知，用户在卡片外自行处理 | 不计入；不增加处理状态或备注流程 |

统计单位是告警事项/轮次，不是日志条数、累计次数或群消息条数。同一轮次发送多张卡片也只计一个事项。

## 主状态与变化

### 日志告警

| 当前状态 | 触发条件 | 结果 |
| --- | --- | --- |
| 尚未创建本轮 | 首次有效日志告警 | 待处理，红色 |
| 待处理 | AI 实际开始执行，或首条人工备注保存成功 | 处理中，橙色 |
| 待处理 | AI 未能实际启动，且没有成功保存的备注 | 仍为待处理，正文说明原因 |
| 待处理或处理中 | 人工填写处理结果并成功提交“标记已处理” | 已处理，绿色 |
| 处理中 | AI 结束/失败、MR 交付/合并、后续备注或同轮新事件 | 保持处理中，更新对应内容 |
| 已处理 | 旧轮次的 AI/MR 结果或迟到旧事件到达 | 只归原轮次；保持已处理，不覆盖人工处理结果 |
| 已处理 | 确认新发生的同类告警 | 创建新轮次，从待处理开始；旧轮次不重开 |

日志卡的“处理中”表示 AI 或人工已开始处理，不等于必然已有人工负责人。标题、颜色和操作区统一按当前主状态展示，不能正文已在处理而标题仍写待处理。

人工可从待处理直接结束本轮，不要求先备注，也不以 AI 结束、存在 MR 或 MR 全部合并为前提；仍须核实已完成或无需修复，并填写一句处理结果。发布、测试、等待上线、AI 无法定位等情况写入正文或备注，不增加第四种主状态。

每轮 AI 至多执行一次。备注不启动、暂停或重试 AI；人工关闭前 AI 尚未启动则不再启动，已在运行则继续本次任务，结果关联原轮次。MR 合并不自动关闭告警，也不自动发布。

### 指标告警

| 当前状态 | 触发条件 | 结果 |
| --- | --- | --- |
| 尚未创建本轮 | 首次有效指标告警 | 待处理，红色 |
| 待处理 | 首条人工备注保存成功，指标尚未恢复 | 处理中，橙色 |
| 待处理或处理中 | 匹配本轮的有效监控恢复事件 | 已恢复，绿色 |
| 待处理或处理中 | 同轮持续告警、观测更新或后续备注 | 保留已有人工进展，不退回待处理 |
| 已恢复 | 旧事件、旧页面或旧卡片回调 | 不重开，不接受新增备注 |
| 已恢复 | 明确的新一次指标告警 | 创建新轮次，从待处理开始；旧轮次不变 |

未备注也可以直接自动恢复。指标卡不提供人工恢复或“标记已处理”按钮；备注写了“已修复”、暂停监控、删除规则或暂时没有新数据，都不代表已经恢复。恢复事件缺少可靠数值时明确显示缺失，不能把旧异常值当成恢复值。

### 备注、终态和并发

- 备注可选、可连续追加，记录填写人和时间；卡片显示最近三条，完整历史可查。既有备注不覆盖、不删除。
- 展开输入、编辑草稿、取消、空白校验失败或保存失败，均不改变主状态；失败保留草稿。
- 两类终态均禁止新增人工备注，旧卡片与旧页面的迟到提交也必须拒绝。已处理日志仍可补充归属原轮次的自动结果，不能据此重新开放人工操作。
- 备注与结束并发时，以服务端保存顺序为准：备注先成功则保留；结束先成功则拒绝后到备注。重复结束不覆盖首次成功的处理结果、人员和时间。
- 不提供独立认领、接管、手动切换处理中、撤销完成或重开旧轮次操作。

## 吊顶和 H5

吊顶标题为“本群未完成告警”，分别展示日志、指标的未完成数量及待处理/处理中分布，只提供一个“查看未完成（总数）”按钮，不再使用 `01/02/03` 定位原消息。

**展示条件：日志待处理 + 日志处理中 + 指标待处理 + 指标处理中 > 0。**

| 变化 | 统计和吊顶行为 |
| --- | --- |
| 没有未完成告警 | 默认不展示，不留零数量卡片或空白占位 |
| 新增首个未完成告警 | 显示吊顶 |
| 待处理变为处理中 | 分布改变，总数不变，继续展示 |
| 待处理为 0，但还有处理中 | 继续展示 |
| 一类已全部结束，另一类还有未完成 | 继续展示，两类统计均保留 |
| 日志成功已处理或指标有效恢复 | 移出对应未完成事项 |
| 最后一个未完成事项结束 | 关闭整个吊顶区域 |
| 后续再次出现未完成事项 | 重新展示吊顶 |

吊顶隐藏不删除群历史消息，也不强制关闭已经打开的 H5。H5 默认展示本群全部未完成事项，可切换日志和指标；完成后从列表移除，当前已打开的完成结果保持只读。

桌面端入口目标为钉钉自身右侧栏，手机目标为钉钉内半浮层。H5 的日志卡和指标卡分别沿用对应钉钉模板的字段、顺序、标题、颜色、备注和按钮，不额外加入图表、插图或指标。外层只承担分类、计数和列表导航。

## H5、群卡片和消息的联动

| 操作或事件 | 业务状态/卡片同步 | 是否新增群卡片消息 |
| --- | --- | --- |
| 本轮首次告警 | 建立本轮事项与首次通知 | 是，首次通知 |
| H5 成功追加备注 | 追加记录，必要时进入处理中，刷新已有卡片 | 是，向来源群发送一张最新卡片 |
| H5 成功标记日志已处理 | 保存结果与终态，刷新已有卡片及统计 | 是，向来源群发送一张已处理卡片 |
| 一次提交同时改变备注和状态 | 作为一次有效业务提交 | 仍只有一张 |
| 在原群卡片内操作 | 更新业务记录和本轮已有卡片 | 不因本次 H5 方案额外重发 |
| 同轮监控事件、AI/MR 进度、指标恢复 | 同步本轮已有卡片及相关统计 | 沿用更新规则，不增加逐次重发 |
| 浏览、筛选、复制、取消、空白内容、保存失败 | 不产生有效业务提交 | 否 |
| 同一次请求重试、重复点击或终态上的无效操作 | 返回原结果或拒绝操作 | 不重复发送 |

新增消息仍属于原告警轮次，不能增加事项数、重置累计次数、继承为新轮次或重新执行 AI。所有已投放卡片展示本轮最新状态，所有按钮依据当前业务状态校验。

不同人或不同提交追加相同文字仍是新记录，不能只按文字去重。同一次请求的重试不重复保存备注或投递消息。业务保存成功但钉钉同步失败时，保留已保存结果，提示同步状态并重试同步，不能让用户再次保存同一条备注。旧的同步结果不能覆盖新的状态。

## 补充确认与后续边界

2026-10-05 用户对原先三项未决事项补充确认如下。这三项不再作为本轮卡片方案的待确认问题；当前卡片设计可以据此收口。

| 事项 | 本轮确认结论 | 留到后续的内容 |
| --- | --- | --- |
| 指标始终收不到恢复事件 | 暂不处理这类例外，当前仍保留待处理/处理中及未完成统计；卡片和 H5 不新增人工恢复或关闭按钮 | 后续可在后台管理中增加关闭入口，具体状态与操作细节到后台功能设计时再讨论 |
| 谁能备注、谁能结束日志 | 所有当前告警群成员均可操作本群告警，包括追加备注和标记日志已处理，不限于指定运维人员，也不要求先认领 | 群成员可登录告警平台，管理与运维权限可在登录后由后台分配；账号开通、角色和权限配置细节留到后续功能设计 |
| 重复聚合及轮次识别 | 以原告警管理平台 `alarm-plaform` 的已有设计和处理逻辑为参考，结合本版已确认的状态与轮次规则接入 | 具体字段适配、事件级去重与乱序验收在实现阶段完成，本轮不另起一套聚合方案 |

“所有群成员可操作”不等于跳过登录身份和来源群校验，也不等于任意企业用户登录即自动获得全部后台权限。已确认的卡片操作范围与后续后台权限管理分别记录，不新增认领、接管或审批步骤。

本轮继续使用“日志由人工结束、指标由监控恢复、终态禁止备注、零未完成隐藏吊顶”。后续后台关闭入口属于例外处置设计，不在本轮把人工关闭伪装为监控已恢复。
