# 钉住消息能力核查

核查日期：2026-10-05。范围为聊天消息的“钉住／取消钉住／钉住消息列表”，不混用 DING 提醒、整个会话置顶、单条消息置顶或互动卡片吊顶。此次只读取官方资料和公开源码，没有发送、钉住或取消任何真实消息，也没有修改群设置。

## 结论与当前取舍

用户已明确限定：告警服务通过钉钉企业应用或机器人可直接调用的公开服务端 API 自动钉住、取消钉住，不接入 CLI 或 MCP。

**按这个条件，截至本次核查，未找到可采用的公开钉住／取消钉住消息 REST API；当前设计排除“未完成自动钉住、完成自动取消钉住”的方案依赖。** 这表示公开资料不足以支持接入，不表示已经证明钉钉内部或所有定向开放渠道都不存在该能力。

前一轮查到的是官方 DingTalk Workspace CLI／IM MCP 的操作能力。将其概括成当前告警服务可用的“开放接口”范围过宽，应予纠正；它不能作为现有企业应用 accessToken 或群机器人 Webhook 可直接完成 Pin／Unpin 的依据。

“后台查询钉住消息数据”和“点击卡片打开原生钉住消息列表”也需分别确认。本次没有找到前者的公开直接 REST 接口，后者仍没有已验证的公开跳转协议或 JSAPI。因此不把“查看全部钉住消息”作为置顶汇总卡片已具备的按钮能力。

## 公开服务端接口的复核范围

本次交叉核查钉钉开放平台的服务端文档与官方生成 SDK，不以搜索无结果单独推断能力不存在。

读取[官方文档总索引](https://open.dingtalk.com/llms.txt)及其链接的[机器人与消息 API 索引](https://open.dingtalk.com/llms-docs/zh-CN/llms-robots-and-messaging.txt)、[群聊与卡片 API 索引](https://open.dingtalk.com/llms-docs/zh-CN/llms-cli-chat-groups-cards.txt)，未找到原生钉住／取消钉住／钉住列表 REST 条目。官方域名精确检索钉住消息、取消钉住、pinMessage、pinMessages、onlyAdminCanPinMsg、messageTop，也未找到相应服务端接口文档。

官方 Go SDK 固定到核查时的提交 `1986c966942afc67b8ccae59d29d57989a45fe76`，读取 `im_1_0`、`im_2_0`、`robot_1_0`、`card_1_0` 和 `impaas_1_0` 的完整 `client.go`，检索 Pin／Unpin／pinMessage／pin_msg／pinned／钉住并枚举客户端方法，没有找到原生消息 Pin／Unpin 或 Pin 列表接口。来源：[即时通信 SDK](https://github.com/alibabacloud-go/dingtalk/blob/1986c966942afc67b8ccae59d29d57989a45fe76/im_1_0/client.go)、[机器人 SDK](https://github.com/alibabacloud-go/dingtalk/blob/1986c966942afc67b8ccae59d29d57989a45fe76/robot_1_0/client.go)、[卡片 SDK](https://github.com/alibabacloud-go/dingtalk/blob/1986c966942afc67b8ccae59d29d57989a45fe76/card_1_0/client.go)。SDK 可能落后于新增接口，因此这只是与文档交叉核查的证据，不能独立证明平台不提供该能力。

可查到的 `CreateTopbox`、`CloseTopbox`、`TopboxOpen`、`TopboxClose`、`CloseTopCard` 属于卡片吊顶／置顶相关能力，不可当作原生消息钉住／取消钉住的替代接口。来源：[互动卡片吊顶 SDK](https://github.com/alibabacloud-go/dingtalk/blob/1986c966942afc67b8ccae59d29d57989a45fe76/im_2_0/client.go#L1178)、[关闭卡片置顶 SDK](https://github.com/alibabacloud-go/dingtalk/blob/1986c966942afc67b8ccae59d29d57989a45fe76/card_1_0/client.go#L6757)。

官方直接接口文档进一步确认：`POST /v2.0/im/topBoxes` 是[创建并开启互动卡片吊顶](https://open.dingtalk.com/document/development/send-group-helper-message.md)，`POST /v2.0/im/topBoxes/close` 是[关闭互动卡片吊顶](https://open.dingtalk.com/document/development/close-interactive-card-ceiling.md)。它们使用企业应用 accessToken 和 `qyapi_chat_manage` 权限，操作对象为互动卡片；不是原生“钉住消息”集合。另外，路径含 `robot-withdraws-pin-message` 的[撤回接口文档](https://open.dingtalk.com/document/development/robot-withdraws-pin-message.md)实际对应 `/v1.0/robot/ding/recall`，撤回的是 DING 提醒，不是取消钉住。

## 历史核查：CLI／MCP 能力（不采用）

以下仅保留此前证据，解释为什么曾查到“钉住”命令；不作为当前接入方案或后续测试任务。

| 操作 | 官方 CLI 原子命令 | 对应 IM MCP 工具 | 主要参数 |
| --- | --- | --- | --- |
| 钉住消息 | `dws chat message set-pin-msg` | `set_pin_message` | `openConversationId`、`openMessageId` |
| 取消钉住 | `dws chat message unset-pin-msg` | `unset_pin_message` | `openConversationId`、`openMessageId` |
| 查询钉住列表 | `dws chat message list-pin-msg` | `list_pin_messages` | `openConversationId`，可选 `cursor`、`count` |

官方文档说明这些命令支持群聊／单聊；钉住后会话成员可见，取消钉住不会删除原消息。列表默认每页 20 条、上限 100 条，有 `hasMore` 时使用 `nextCursor` 继续查询。来源：[官方会话与群聊命令参考](https://github.com/DingTalk-Real-AI/dingtalk-workspace-cli/blob/main/skills/mono/references/products/chat.md)、[官方意图与命令映射](https://github.com/DingTalk-Real-AI/dingtalk-workspace-cli/blob/main/skills/mono/references/intent-guide.md)。

当前源码还提供 `chat +messages-set-pin`、`chat +messages-unset-pin`、`chat +messages-list-pin` 三个 Shortcut。它们向 `im` MCP 发请求，附带 `openConversationId` 和兼容字段 `cid`；设置／取消还需要 `openMessageId`。此处的消息 ID 不能直接以卡片的 `outTrackId` 或发送回执 `processQueryKey` 替代。来源：[当前核查提交的 Shortcut 实现](https://github.com/DingTalk-Real-AI/dingtalk-workspace-cli/blob/3f0fc94111b1f9cd34e47468980b1f1a723ca69a/internal/shortcut/chat/chat_message.go#L2304)、[原子命令实现](https://github.com/DingTalk-Real-AI/dingtalk-workspace-cli/blob/3f0fc94111b1f9cd34e47468980b1f1a723ca69a/internal/helpers/chat.go#L9588)。

## CLI／MCP 的认证与边界（不采用）

官方 CLI 的通常接入路径是组织开启 CLI 访问后，由用户完成 OAuth 登录授权。使用自建应用凭证也仍需登录授权；用户身份以组织和用户组合区分。MCP 传输实现发送用户令牌；与单独的 `dws api` 应用级 App Token 调用路径不同。来源：[官方接入和授权说明](https://github.com/DingTalk-Real-AI/dingtalk-workspace-cli/blob/main/README_zh.md#开始使用)、[MCP 传输认证源码](https://github.com/DingTalk-Real-AI/dingtalk-workspace-cli/blob/3f0fc94111b1f9cd34e47468980b1f1a723ca69a/internal/transport/client.go#L873)。

群设置中存在 `onlyAdminCanPinMsg`，控制谁可以钉住群消息；这与 `onlyAdminCanSetMsgTop`（谁可以置顶群消息）分开。因此自动处理账号是否能操作，取决于授权及所在群的设置，不能仅凭发送机器人已经入群判断。来源：[群设置字段定义](https://github.com/DingTalk-Real-AI/dingtalk-workspace-cli/blob/3f0fc94111b1f9cd34e47468980b1f1a723ca69a/internal/helpers/chat.go#L8090)。

此前路径还存在以下未验证项。由于用户已排除 CLI／MCP，本任务不再为这条路径创建测试群或推进接入：

- 现有互动卡片和机器人发送的消息能否使用相应消息 ID 完成钉住、查询及取消钉住；已查文档没有对这些消息类型作出明确保证。
- 卡片发送返回值与 IM `openMessageId` 的对应获取方式。不能假设两种 ID 相同。
- 本组织是否已开通所需 CLI／MCP 能力，以及具体授权范围；本次未查到这三个操作各自的独立权限 scope 清单。
- 取消钉住对多人曾钉住同一条消息的具体行为，以及失败重试的实际结果。
- Mac、iOS、Android 的展示，以及钉住列表内对互动卡片后续更新的呈现。

“官方已公开”与“在当前账号、目标群、目标卡片上已经验证成功”应分开记录。官方仓库保留了一份历史真实测试报告，曾出现 Pin／Unpin 的会话字段未被后端正确识别；当前 Shortcut 已有兼容字段，但本次没有真实调用，因此既不将历史失败当作今天仍不可用，也不声称链路已经验证通过。来源：[官方历史 MCP 测试问题记录](https://github.com/DingTalk-Real-AI/dingtalk-workspace-cli/blob/main/docs/shortcut-backend-mcp-issues.md)。

## 从卡片打开“全部钉住消息”

钉钉官方产品说明列出了客户端原生入口：聊天快捷栏中的“钉住消息”、点击消息下方“某某钉住了这条消息”，以及手机的设置 → 聊天记录 → 钉住消息。其中点击消息下方提示可以打开列表并定位那条消息。来源：[钉钉官方产品说明](https://page.dingtalk.com/wow/dingtalk/default/dingtalk/ObC93W66RDlimrW8y7Vg)。

本次对[官方链接跳转规范](https://open.dingtalk.com/document/development/link-jump-specification)及 `dingtalk-jsapi@3.2.9` 的类型声明核查，未找到可供外部卡片直接打开原生钉住列表的已确认协议／公开 JSAPI。不得自行猜测一个 `dingtalk://` 地址后作为正式方案。

目前不将“查看钉住消息”配置为置顶汇总卡片的已确认入口；也不通过自有页面转接 MCP 来绕过用户的接入限制。编号查看告警详情是另一项需求，其原始消息定位、原生话题面板与自有 H5 详情的验证边界，继续以[消息详情跳转核查](消息详情跳转核查.md)为准。

## 对现有告警流程的影响

保留已经确认的置顶汇总卡片与告警卡片设计：

- 汇总卡按业务状态统计待处理和处理中；日志已处理、指标已恢复后，从未完成汇总中移除。
- 日志卡继续使用待处理／处理中／已处理；首条备注成功后表示有人跟进，完成后禁止追加备注。
- 不将钉住状态作为告警业务状态，不新增自动钉住／取消钉住动作，不依赖原生钉住列表提供告警入口。

只有以后获得明确受支持的直接服务端 API 文档、认证方式和权限要求，才重新评估这条路径。本次没有安装 CLI、连接 MCP 或对真实群消息执行 Pin／Unpin。
