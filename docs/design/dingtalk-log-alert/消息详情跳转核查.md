# 消息详情跳转核查

核查日期：2026-10-05。范围：钉钉官方文档、官方 Workspace CLI 公开资料及 `dingtalk-jsapi@3.2.9` 发布包。包含文档、源码核查、个人卡片助手投放及专用测试群实测。Mac 已确认 `searchDesc` 可被群内搜索命中，点击搜索结果会回到群聊并高亮对应消息；卡片按钮直接打开原生话题侧栏和手机半浮层仍未验收。CLI/MCP 仅为历史核查资料，不纳入接入方案。

用户提供的 Mac 截图显示：点击引用消息后，右侧打开标题为“话题”的面板，展示原消息及回复。用户接受置顶卡片 `01 / 02 / 03` 打开对应告警详情的类似体验，不要求必须滚动到群消息位置。

**最新方案选择：** 用户已选择“吊顶分别统计日志与指标 → 按钮打开 H5 当前群未完成列表 → H5 有效提交后发送最新卡片”。以[吊顶与告警处理工作台设计](吊顶与告警处理工作台设计.md)为当前流程依据。本文的编号定位、搜索、原生话题和候选入口记录作为能力核查历史，不再要求主流程依赖原消息定位。

## 结论

**卡片按钮打开 PC 侧边栏、手机底部半浮层，官方有明确支持；按钮直接打开某条已有消息的原生“话题”详情，目前尚未核实为可供该应用使用的公开能力。** 两者需要分别验证，不能把前者的成功当作后者成功。

| 点击目标 | 已有证据 | 本次判断 |
| --- | --- | --- |
| 本系统的告警详情 H5 | 官方列出卡片链接的 PC 侧栏、移动半浮层及多端分流协议 | 可按公开协议设计，仍需真机点击验证 |
| 已有群消息的原生“话题”面板 | 用户截图证明客户端功能存在；SDK 包存在 `internal.chat.previewMessage` | 未核实第三方调用权限、公开 ID 换取方式及 Mac 支持，不能承诺已接通 |
| 群里的某一条消息位置 | SDK 包存在 `internal.chat.focusMessage`；公开会话跳转文档只接收会话 ID | 未核实可用的公开消息定位接口 |
| 仅凭 `outTrackId` 打开卡片实例 | 创建投放 API 说明该字段唯一标识卡片，没有给出详情跳转 URL | 本次未找到可承诺的原生卡片实例详情入口 |
| 用专属搜索码查找原卡 | 在专用群通过公开 REST 接口发送两张卡；Mac 群内分别搜索命中，点击结果返回并高亮原消息 | 搜索路径实测可用；不代表卡片按钮可以直接发起搜索 |

## 可使用的公开链接协议

卡片按钮的“链接跳转”支持固定链接和变量链接；可按客户端配置不同链接。普通 HTTP 链接的默认效果与侧栏不同，应显式采用跳转协议。[交互方式](https://open.dingtalk.com/document/development/interactive-mode)

官方协议如下，内层 URL 和外层协议值均须分别 URI 编码。`83` 是文档示例的半浮层高度百分比。[链接跳转规范](https://open.dingtalk.com/document/development/link-jump-specification)

```text
PC：
dingtalk://dingtalkclient/page/link?pc_slide=true&url=${encodedDetailUrl}

移动端：
dingtalk://dingtalkclient/action/im_open_hybrid_panel?panelHeight=percent83&hybridType=online&pageUrl=${encodedDetailUrl}

多端统一：
dingtalk://dingtalkclient/action/open_platform_link?pcLink=${encodedPcLink}&mobileLink=${encodedMobileLink}
```

链接构造示意，`detailUrl` 应传入本系统真实、可访问的告警详情地址：

```javascript
const target = encodeURIComponent(detailUrl);
const pc = `dingtalk://dingtalkclient/page/link?pc_slide=true&url=${target}`;
const mobile = `dingtalk://dingtalkclient/action/im_open_hybrid_panel?panelHeight=percent83&hybridType=online&pageUrl=${target}`;
const buttonUrl = `dingtalk://dingtalkclient/action/open_platform_link?pcLink=${encodeURIComponent(pc)}&mobileLink=${encodeURIComponent(mobile)}`;
```

H5 页面内还可调用 `dd.biz.util.openSlidePanel({url, title})`，但该接口文档只标注 PC 支持，Android/iOS 不支持；它不是直接打开原消息的接口。[打开侧边面板](https://open.dingtalk.com/document/development/open-side-panel)

## 原消息与原生卡片详情的边界

公开会话跳转 `dd.biz.chat.toConversationByOpenConversationId` 只定义 `openConversationId`，没有消息 ID 参数；文档说明需要鉴权，当前人不是目标会话成员时会提示会话不存在。这只能作为打开会话的证据。[根据 openConversationId 跳转到对应会话](https://open.dingtalk.com/document/development/redirects-to-the-specified-session-based-on-the-openconversationid)

创建并投放卡片 API 中，`outTrackId` 标识卡片实例，`openSpaceId` 标识投放场域。IM 投放结果的 `carrierId` 文档解释为 `processQueryKey`，用途是查询消息已读列表。文档没有将它定义为原消息详情 URL，也没有说明它等同于 `openMessageId` 或数字 `messageId`。[创建并投放卡片](https://open.dingtalk.com/document/orgapp/create-and-deliver-cards)

官方 Workspace CLI 支持机器人在群聊 Markdown 中引用回复，使用 `--reply <openMessageId>` 与 `--ref-sender <senderOpenDingTalkId>`。这证明引用关系可以通过相关发送能力构造，不代表任意卡片按钮能用相同 ID 打开原生话题面板。[会话与群聊命令参考](https://github.com/DingTalk-Real-AI/dingtalk-workspace-cli/blob/main/skills/mono/references/products/chat.md)

SDK 发布包中有以下线索，但本次不将其纳入正式依赖：

| SDK 声明 | 参数 | 发布包注释与局限 |
| --- | --- | --- |
| `internal.chat.previewMessage` | `messageId: number`、`conversationId: string` | 注释为根据消息 ID 跳转消息详情；只标注 iOS/Android 4.6.25。位于 `internal` 命名空间 |
| `internal.chat.focusMessage` | 同上 | 注释为在会话页定位消息；同属 `internal` |
| `biz.util.acitveConversation` | `cid`，可选 `messageId`、`keyword`、`createdAt` | 注释为激活会话窗口，标注 Mac/Windows 6.0.8；仅发现内部发布文件的类型声明，未找到相应公开使用说明 |

来源：[SDK 固定版本发布包](https://registry.npmjs.org/dingtalk-jsapi/-/dingtalk-jsapi-3.2.9.tgz)，对应文件为 `package/lib/common/api/internal/chat/previewMessage.d.ts`、`focusMessage.d.ts` 和 `package/lib/common/api/biz/util/acitveConversation.d.ts`。包内存在声明不等于当前企业应用具有调用权限；不同消息 ID 也不能自行互换。

## 对置顶卡片的设计建议与验收

编号继续表示当前列表位置；每个按钮绑定对应告警轮次的实际目标，列表刷新后一起更新，不让 `01` 成为业务身份。完成或恢复后，从列表移除；详情仍展示最终结果，禁止继续添加备注。

优先验证公开协议的 H5 方案：Mac 在侧栏展示对应告警详情，手机在底部半浮层展示同一详情。内容和主卡片使用同一告警轮次的数据；这是一种可实现的类似体验，但不是钉钉原生引用回复面板。

最小实测可先使用钉钉卡片助手，确认点击协议，再进入仅测试参与者的群验证置顶编号映射。官方卡片平台的 IM 与吊顶投放默认目标是“钉钉卡片助手”。[卡片平台投放卡片实例](https://open.dingtalk.com/document/development/card-delivery-instance-for-card-platform)

实测记录应分别标记：按钮协议能否唤起、Mac 侧栏是否正确、手机半浮层是否正确、目标告警是否正确、已完成状态是否只读。模板编辑器内预览不能替代客户端协议验证。若后续拿到钉钉公开支持的原生话题链接及 ID 获取方式，再测试并替换按钮目标；不需要改变编号式置顶卡片布局。

## searchDesc 搜索验证（2026-10-05）

官方[创建并投放卡片](https://open.dingtalk.com/document/orgapp/create-and-deliver-cards)文档明确提供 `imGroupOpenSpaceModel.searchSupport.searchDesc`，用于消息展示与搜索，最多 200 字符。该字段提供搜索索引描述，不等同于直接消息跳转协议。

最初在已有“告警编号侧栏跳转验证”草稿的“测试卡片”弹窗发现独立的“消息搜索文案”输入项，通过该入口发送了两张卡片到当前用户的“钉钉卡片助手”：

| --- | --- | --- |
| A | `[搜索验证 A] 独立搜索字段测试` | `QALM7K4N2A 搜索验证甲` |
| B | `[搜索验证 B] 独立搜索字段对照` | `QALM9V6P3B 搜索验证乙` |

两张卡复用同一测试模板，搜索码没有写入正文或缩略文案，以区分 searchDesc 索引与正文命中。官方设计器完成发送；Mac 客户端会话摘要分别显示测试 A、B，确认已送达。没有向业务群发送，也没有发布模板。

### 按未完成状态搜索的补充验证

官方[新增或者更新卡片的场域信息](https://open.dingtalk.com/document/development/add-field-interface)接口为 `PUT /v1.0/card/instances/spaces`，请求支持更新 `imGroupOpenSpaceModel.searchSupport.searchDesc`。这提供了修改描述的接口，但不能仅凭接口成功认定已投放消息的搜索索引会同步刷新。

2026-10-05 06:03:40（Asia/Shanghai），给上述 A、B 两个既有测试实例的搜索描述追加同一个测试标记 `ALMOPEN8K6`，保留原专属搜索码；两次均返回 HTTP 200、`success=true`、`result=true`，没有重发消息。在随后约一分钟内的 Mac 群内搜索中，新标记没有命中任何聊天记录；对照搜索原码 `GQALM7K4N2A` 仍能找到 A。

本轮不能确定是索引延迟，还是场域信息更新未同步到已投放消息。由于追加标记尚未命中，没有继续把“完成后删除标记”当作已验证能力。**暂不采用动态搜索标记作为权威的未完成告警列表；静态专属码查找原卡的既有结论不变。** 这里仅修改模拟测试卡的搜索描述，没有改变真实业务告警状态。

### 快速找到未完成告警的替代入口

以下为候选设计，不表示已完成接入：

- **固定入口与当前清单**：置顶卡片展示“未完成 N 条（待处理/处理中）”，按钮打开本系统按当前群过滤的未完成列表；`01 / 02 / 03` 也可直接绑定相应告警详情地址。PC 侧栏和移动半浮层使用前述公开链接协议。列表与原告警使用同一份状态，完成后从列表移除；历史消息定位保留为辅助入口。需要提供相应 H5 列表/详情页面并实测客户端。
- **群内卡片清单**：用户主动请求时，由机器人返回当前未完成告警的清单卡片；需要时再返回某个告警的当前详情卡。公开卡片回传请求和投放能力可组合承载此流程，不依赖搜索历史消息；这是应用自建功能，需要处理同一告警的多个展示入口与最新状态一致。可通过置顶按钮请求，也可设计为 `@机器人 待处理`。
- **钉钉工作待办**：有公开创建和更新接口，业务完成后可更新 `done=true`。适合要在钉钉原生待办列表集中处理的场景，但需要确定执行人、维护任务映射并同步完成状态。当前创建工作待办接口要求业务详情 `detailUrl`，不能将其描述成“无需自有详情页，直接定位旧消息”。来源：[创建工作待办](https://open.dingtalk.com/document/orgapp/add-dingtalk-to-do-task)、[更新待办](https://open.dingtalk.com/document/orgapp/updates-dingtalk-to-do-tasks)。

固定入口有接入条件：新版[创建并开启互动卡片吊顶](https://open.dingtalk.com/document/development/send-group-helper-message)对群聊要求群模板创建的场景群，或者安装了群聊酷应用的群。普通群仅添加机器人不等于已经获得吊顶能力；不符合条件时，可先用机器人按需返回清单。
