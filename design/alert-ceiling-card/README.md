## 展示与交互

卡片顶部显示「未结束告警 · 数量」，中间并排放置日志、指标两个统计区。每个统计区展示本组数量、状态数量分布，以及 `01 ↗`、`02 ↗` 等原卡入口。底部提示「点编号定位原卡」。

统计数字用于概览，具体编号入口用于定位一张确定的原卡。吊顶不展开告警详情，不展示认领人、认领提示或备注，也不提供处理、关闭等业务操作。

| 区域 | 当前设计参数 |
| --- | --- |
| 预览尺寸 | 在设计器 280 × 118 的吊顶区域、100% 缩放下检查 |
| 顶部标题 | 12 px，加粗，行高 16 px |
| 统计分组 | 左侧日志、右侧指标；各宽 124 px，间距 8 px，外侧边距 12 px |
| 分组名称 | 10 px，行高 13 px |
| 分组数量 | 20 px，加粗，行高 22 px |
| 状态分布 | 9 px，行高 11 px |
| 编号入口 | 10 px，白色小块，附跳转箭头 |
| 浅色背景 | 日志 `#F3F5F8`，指标 `#EEF5FD` |
| 底部提示 | 9 px，行高 11 px |

每组编号入口放在横向滚动容器中。告警增多时可以横向查看后面的入口，统计包含完整列表，吊顶不随数量增加而纵向拉长。各端的实际触控、滚动和深色模式仍需在正式接入时验证。

没有未结束告警时，两组数量均为 0，不显示编号入口，底部显示「当前没有未结束告警」。单个分组为空时，该组显示 0，另一组正常展示。

## 列表范围与结束条件

统计和入口都只包含本群关联的未结束告警。日志、指标分别汇总；普通状态通知不进入这个列表。同一轮告警在同一群内只占一个入口，重复通知更新该项，不重复增加数量。

| 变化 | 吊顶结果 |
| --- | --- |
| 新增本群未结束告警 | 加入对应分组，增加数量，生成编号入口 |
| 待处理变为处理中 | 保留入口，更新状态分布，总数不变 |
| 日志告警按业务规则确认结束 | 移除入口，减少数量，剩余项重新编号 |
| 指标告警收到匹配本轮的监控恢复事件 | 移除入口，减少数量，剩余项重新编号 |
| 只填写备注或记录处置措施 | 不据此认定已经结束 |
| 本轮已结束后发生明确的新一轮告警 | 按新一轮记录加入，并关联新一轮原卡 |
| 全部结束 | 清空入口，显示零告警状态 |

移除吊顶入口不删除群里的原始卡片或告警历史。是否已经结束，以告警服务确认的业务状态为准；不能根据备注中写了“已修复”、卡片颜色、暂时没有新通知或通知静默来推断。

### 与指标卡设计的衔接

主分支已合入的[指标告警卡片实现说明](../metric-alert-card/指标告警卡片实现说明.md)规定：监控状态只有 `firing` 和 `resolved`，备注不改变监控状态，也没有人工标记处理中的操作。指标告警必须在有效恢复事件到达后才从吊顶移除。

当前吊顶设计稿两组都使用「待处理 / 处理中」的模拟统计位。**指标分组的真实状态文案与统计映射仍需在接入时对齐**：不能直接把“已有备注”当成真实的“处理中”状态，也不能为了填满统计位新增指标业务状态。如果接入数据只有 `firing/resolved`，应按实际状态调整为“告警中”等对应文案，并同步更新模板。此项是跨卡片状态适配的待办，不代表后端已有统一状态模型。

## 动态编号规则

`01`、`02`、`03` 是当前分组内的位置，不是告警的永久编号。日志和指标两组分别从 `01` 开始，删除中间项后，后面的项自动前移，重新生成连续序号。剩余项的相对顺序保持稳定，新增项放在本组末尾。

| 变化 | 01 | 02 | 03 | 本组数量 |
| --- | --- | --- | --- | ---: |
| 初始 | 告警 A | 告警 B | 告警 C | 3 |
| B 结束 | 告警 A | 告警 C | — | 2 |
| 新增 D | 告警 A | 告警 C | 告警 D | 3 |

显示序号至少两位，不累计历史数量，不复用业务 ID 作为序号。若当前未结束告警本身超过 99 条，序号自然显示 100 等完整数字；这表示当前列表规模，不是历史累计编号。

每一项同时携带稳定的告警轮次 ID 和对应群内的原卡链接。重排只改变展示序号，不改变告警身份或跳转目标。告警 C 从 `03` 变为 `02` 后，新的 `02` 仍定位 C；服务端不得通过“当前第二项”的位置反查来替代点击时绑定的告警关联。

## 原卡跳转

点击编号应直接定位到该群中对应的原始告警卡片。模板通过当前循环项的 `original_card_url` 绑定 URL 动作，序号和链接在同一个列表项中传递。

目前没有可验证的真实钉钉原卡消息链接。所有可导入模拟场景的链接均为空，点击时明确提示「此示例尚未绑定原卡消息链接」，不会伪装成已经跳转成功。需要实际消息定位链接才能验证桌面端和移动端行为。

用于调用卡片更新接口的 `outTrackId` 与群消息定位地址是不同用途的数据。不能直接把模板 ID、卡片实例标识或打开群聊的链接当成已验证的原卡定位链接；本设计不约定未经验证的钉钉深链格式。

## 状态变化后如何同步

钉钉提供已有卡片的数据更新能力，官方示例也包含置顶卡片更新，具备同步展示的基础能力。参见[钉钉官方群卡片示例](https://github.com/open-dingtalk/h5app-scene-group-demo)与[更新卡片接口](https://open.dingtalk.com/document/development/interactive-card-update-interface)。

后端应维护本群吊顶卡片实例与告警原卡的关联。业务状态确认变化后，对同一张吊顶卡片执行以下步骤：

1. 读取该群最新的未结束告警，按日志、指标分组，并保留稳定顺序。
2. 在每组内重新生成连续序号，保留每项自身的告警 ID 与原卡链接。
3. 从这一份数据计算分组总数及有效状态分布。
4. 将列表、序号、链接和状态计数作为同一份快照提交更新，保证数字与入口对应。

原卡状态更新和吊顶更新都应以已经保存的告警状态为准。吊顶不会自行读取其他卡片的文字来判断告警是否结束。

“实时更新”在这里指状态变化后由服务端主动同步，实际存在接口和网络延迟。本设计未承诺具体秒数，也没有实现运行中的同步服务。

多条告警同时变化时，更新应按群收敛到最新快照，避免较旧的请求覆盖较新的列表。失败后重试最新业务状态，而不是反复发送早先的旧列表；吊顶更新失败不回滚已确认的告警结束状态。具体重试、限流和顺序控制复用接入项目已有能力，在实现时确定。

## 模板数据约定

以下是当前设计器字段，不是数据库结构或生产发送接口。`mixed.json` 等文件包含 `editorData`、`type: onebox` 等导入封装，不能直接作为卡片发送 API 的请求体。

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `log_alerts` | 列表 | 本群未结束日志告警，按展示顺序传入 |
| `metric_alerts` | 列表 | 本群未结束指标告警，按展示顺序传入 |
| 每项 `id` | 字符串 | 稳定的告警轮次标识，不随展示位置变化 |
| 每项 `number` | 字符串 | 本次列表中的显示序号，例如 `01` |
| 每项 `title` | 字符串 | 简短告警名称，供识别对应项使用 |
| 每项 `status` | 字符串 | 当前模拟为待处理或处理中；真实指标状态适配见前文 |
| 每项 `original_card_url` | 字符串 | 对应群内原卡的有效消息定位地址；当前模拟为空 |
| 每项 `has_link` | 数字 | 1 表示该项有链接，0 显示缺少链接提示；正式接入先验证地址再赋值 |
| `log_pending` / `log_processing` | 数字 | 日志分组状态计数 |
| `metric_pending` / `metric_processing` | 数字 | 指标分组的模拟状态计数，正式文案和映射需对齐指标状态 |

总数及分组数量由列表长度表达式计算。状态计数由同一份列表计算后传入。删除最后一项时必须传入空列表及零计数，使旧入口清除；不能依赖省略字段来表达清空。

服务端接入时需校验告警轮次、群归属、状态和原卡关联。显示序号不承担身份校验、去重或权限控制职责。

## 模拟场景与复现

生成器仅依赖 Python 标准库，不连接任何告警服务。运行后先进行中间项移除自检，再生成以下文件：

```sh
python3 design/alert-ceiling-card/build_preview.py
```

| 文件 | 场景 |
| --- | --- |
| [mixed.json](mixed.json) | 默认：日志 2 条、指标 2 条，各组模拟为待处理 1 条、处理中 1 条 |
| [claimed.json](claimed.json) | 日志第一条从待处理转为处理中，总数不变；文件名沿用早期模拟名称，界面不显示认领文案 |
| [finished.json](finished.json) | 仅剩一条日志告警，重排为 01；指标组清空 |
| [empty.json](empty.json) | 两组均为空，显示零告警状态 |
| [overflow.json](overflow.json) | 日志 8 条、指标 2 条，验证入口横向滚动 |
| [three-alerts.json](three-alerts.json) | 日志 A、B、C 三条，序号为 01、02、03 |
| [middle-resolved.json](middle-resolved.json) | B 移除后保留 A、C，序号为 01、02，总数变为 2 |

在本吊顶草稿的「更多 → 导入卡片模板」中选择场景文件，确认后切换「预览模式」。导入会覆盖当前草稿数据，查看其他场景后用 `mixed.json` 恢复默认设计。不要将这些场景导入日志或指标原卡模板。

自检在内存中使用 `example.invalid` 地址区分不同原卡目标，检查移除 B 后 C 的 ID 和目标保留、序号前移、状态计数正确，以及空列表计数归零。这些地址不写入导入文件，自检不代表真实钉钉跳转联调通过。
